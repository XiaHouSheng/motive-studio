# Motive Studio — UI/UX Design & Refinement Prompt

> 来源：用户提供的 UI/UX 设计与打磨计划（执行任务的 Prompt）。
> 配套文档：PRODUCT_SPEC.md（产品规格）、.agent/prompts/（4 个生产 Prompt）。

1. 项目定位

项目名称：Motive Studio

产品定位：AI-powered structured thinking workspace（AI 结构化思考工作台）。

Motive Studio 不只是 AI Chat，也不局限于数学解题。它希望帮助用户围绕一个具体问题持续探索，通过自由对话、上下文关联、结构化整理与结果归档，将零散的思考沉淀为清晰、可迭代的成果。

当前 MVP 主要用于 AI 解题与学习，但 UI 架构必须为未来扩展到编程、研究、写作和项目规划保留空间。

品牌关键词：

* Professional
* Thoughtful
* Minimal
* Structured
* Calm
* AI-native
* Developer-tool quality

设计目标：打造一个看起来像成熟专业软件、具有清晰信息层级和高效交互的工作台，而不是套用常见的 AI SaaS Dashboard 模板。

2. 核心产品结构：三栏工作台

保留现有三栏架构，不要擅自改成普通聊天页面、标签页式应用或传统 Dashboard。

A. 左侧：题组与题目导航

职责：切换题组、选择题目、管理工作对象。

设计要求：

* 采用紧凑、稳定的侧边栏。
* 清楚区分题组与题目层级。
* 当前选中题目具有明确但克制的视觉状态。
* 支持长标题的截断、悬停查看和合理换行。
* 新建题组、新建题目等操作应易于发现，但不应喧宾夺主。
* 图标、文字、缩进和间距形成清晰的信息层级。
* 侧边栏支持折叠，以便在小屏幕下释放空间。
* 避免每个项目都套上独立卡片或厚重边框。

未来可将“题组/题目”抽象为通用的工作空间、项目与工作对象，但当前不要为尚未实现的功能增加无效入口。

B. 中间：正式内容与结构化成果

职责：呈现当前工作对象的正式内容。

当前包括：

* 初始题目与题解。
* 有序的解题步骤。
* 每个步骤对应的“进入讨论”入口。
* 归档后更新的正式解释与补充内容。

设计要求：

* 中间区域是整个界面的主要阅读区域。
* 优先保证长文本、公式、代码块和分步骤内容的可读性。
* 正式内容应有清晰的标题、步骤编号、正文、公式与辅助说明层级。
* “进入讨论”应与对应步骤形成明确的视觉关联。
* 用户应能快速定位某一步，并在讨论结束后回到正式内容。
* 可以为步骤提供轻量级悬停操作，但不要让每一步出现过多按钮。
* 适当利用留白建立阅读节奏，避免所有内容挤成密集的文本墙。
* 公式、代码和长文本需要有合理的宽度控制，不能为了填满屏幕而无限拉宽。
* 不要将正式题解和原始聊天记录混在一起。

正式内容代表当前沉淀下来的成果；讨论中的临时想法、待验证推测与探索过程应保持独立。

C. 右侧：自由讨论 ChatBox

职责：围绕当前工作对象进行连续、多轮、自由的讨论。

重要产品规则：

* 用户可以询问任何相关或延伸问题，不需要手动选择 Tag。
* 用户不需要为每条消息指定所属步骤。
* 系统在后台自动判断消息与哪些步骤相关。
* 用户可以从某一步进入讨论，但入口步骤不构成讨论范围限制。
* 同一轮消息可以关联多个步骤。
* 归档后，系统将相关讨论整理为各步骤的上下文，并更新正式内容。

UI 设计要求：

* 保持熟悉、高效的聊天交互。
* 消息列表与输入框层级清楚。
* 输入框应支持多行输入，发送操作明显但不夸张。
* 用户能够自然地连续提问，不必理解内部 Tag 机制。
* 可以通过轻量状态提示展示正在思考、正在归档、归档完成或失败等状态。
* 不要将 Tag 作为主要聊天 UI 元素，也不要让用户承担手动分类工作。
* 讨论与正式内容应有清楚的视觉区别。
* 归档属于有意义的操作，需要明确状态反馈，并避免重复提交导致重复更新。
* 归档失败时，应保留对话内容，并提供重试入口。

3. 视觉设计方向

整体风格

采用现代专业桌面软件的设计语言，参考专业开发工具、知识工作空间和成熟编辑器的设计原则。

不要直接复制任何参考产品的界面。

视觉特点：

* 中性、克制、干净。
* 低饱和度背景。
* 清晰的排版与空间层次。
* 细腻的边框和分隔线。
* 少量品牌强调色。
* 高质量的悬停、选中、焦点与加载状态。
* 通过排版、留白和对齐形成精致感，而不是依靠大量装饰。

色彩系统

建议先建立完整的 Design Tokens，再应用到组件。

默认方向：

* 主背景：中性浅灰白。
* 内容区域：白色或与主背景轻微区分的中性色。
* 侧边栏：略有区别的中性背景。
* 正文：深灰黑。
* 次级文字：中性灰。
* 边框：低对比度灰色。
* 品牌强调色：沉稳的深蓝、蓝紫或靛蓝。
* 成功、警告、错误：使用语义化颜色，仅在需要时出现。

强调色只用于重要操作、当前选中状态、键盘焦点和少量关键提示。

避免：

* 大面积渐变背景。
* 过度使用紫色 AI 风格。
* 玻璃拟态与强烈发光效果。
* 大量彩色卡片。
* 所有组件都有圆角、阴影和边框。
* 通过颜色区分每一个普通元素。

同时提供可维护的 Light/Dark Theme 设计基础；若项目当前只实现一种主题，优先把这一主题打磨完整，不要为了主题切换而牺牲核心体验。

4. 布局与尺寸原则

三栏布局需要根据内容密度分配空间，而不是平均分栏。

建议：

* 左侧导航：约 220–260px。
* 中间内容：优先获得最大的阅读空间。
* 右侧讨论：约 320–400px。
* 中间与右侧之间使用清晰但低调的分隔线。
* 允许用户按需要折叠左侧导航或收窄辅助区域。
* 长内容区域独立滚动，避免三栏滚动相互干扰。
* 页面切换时尽量保持用户当前的阅读位置与讨论状态。

上述尺寸是桌面端的起始参考，不是硬编码要求。请根据现有组件、窗口尺寸和真实内容进行调整。

不要把所有内容挤在同一条水平线上，也不要让三栏都出现过多嵌套容器。

5. Typography 与内容排版

建立明确的文字层级：

* 页面标题：简洁、清晰。
* 题目标题：具有足够的识别度。
* 步骤标题：醒目但不应压过页面标题。
* 正文：保证长时间阅读的舒适性。
* 辅助信息：低对比度但仍然清晰可读。
* 代码、公式和变量：使用适合其语义的排版方式。

数学公式需要正确渲染，长公式支持合理换行或横向滚动。

代码块需要清晰的背景、等宽字体与必要的复制功能。

不要为了营造视觉层级而使用过多字体大小、粗细或装饰线。

6. 关键交互状态

请检查并设计以下状态：

1. 尚未选择题目。
2. 正在加载题目。
3. 正式题解为空或尚未生成。
4. 当前步骤被选中或正在讨论。
5. ChatBox 为空。
6. AI 正在生成回答。
7. AI 回答生成失败。
8. 正在进行 Tag 关联分析。
9. 正在归档。
10. 归档成功。
11. 归档失败及重试。
12. 归档后正式内容发生更新。
13. 用户切换题目时存在未完成的生成任务。
14. 小屏幕或窄窗口下的布局。

状态反馈应清晰、克制且一致。

不要通过动画掩盖加载时间，也不要在后台任务仍然执行时显示虚假的成功状态。

7. 动效与微交互

使用轻量、快速、可预测的动效：

* 侧边栏折叠与展开。
* 步骤选中状态变化。
* 按钮悬停与按下。
* ChatBox 消息出现。
* 归档进度与成功反馈。
* 面板宽度变化。

动效应服务于状态理解和空间关系，不应成为主要视觉表现。

支持减少动态效果的系统偏好设置。

8. 响应式设计

桌面端是核心体验，但不能只把三栏等比例缩小。

窄屏时：

* 左侧题目导航可以转为抽屉或独立导航面板。
* 正式内容与讨论面板应采用合理的切换或分层布局。
* 保留返回当前题解和当前讨论的快捷路径。
* 不要让用户在手机上同时看到三个拥挤的区域。
* 公式、代码、输入框和操作按钮不能溢出视口。
* 控件应有适合触控的交互尺寸。

优先保证任务连续性与内容可读性，而不是强行保持桌面端的视觉布局。

9. 技术与实施约束

开始前先阅读现有项目：

* 了解当前框架、目录结构、组件和样式系统。
* 找出已有的三栏布局、题组导航、题解步骤与 ChatBox 实现。
* 尽量复用现有组件和数据结构。
* 不要在没有必要的情况下替换整个 UI 框架。
* 不要为了视觉效果引入大量依赖。
* 将重复的颜色、间距、圆角、字体和布局尺寸抽象为统一的设计变量。
* 保持组件职责清晰，避免把所有界面逻辑集中在单个超大组件中。

本次任务以 UI/UX 质量为主，不要擅自改动核心业务流程、Tag 算法、归档算法或数据模型。

如果发现现有交互存在明显问题，请先区分视觉问题与产品逻辑问题；只在必要时调整交互，并保持原有功能可用。

10. 验收标准

完成后应达到以下目标：

* 第一眼看起来像成熟的专业软件，而不是模板化 AI 聊天应用。
* 三栏的职责清晰，用户能快速理解每个区域的作用。
* 正式解题内容易读，讨论区域易用，导航紧凑。
* 进入讨论和返回正式内容的路径自然。
* 用户不需要理解 Tag 机制即可完成任务。
* 归档状态明确，失败可恢复。
* 长题目、长对话、公式和代码不会破坏布局。
* 桌面端比例协调，窄屏下仍然可用。
* 所有主要按钮都具有真实、正确的交互行为。
* 不添加没有实际功能的装饰性控件。
* 不为了视觉效果牺牲阅读效率、信息密度或操作效率。

请直接基于现有代码实施修改。先检查当前实现，再确定具体改动；完成后运行项目已有的检查与构建命令，并总结改动内容、涉及文件和仍存在的问题。
